```
│   └── main.js           # единственная инициализация: Swiper-слайдеры, carousel-nav, фильтры, аккордеоны, мобильное меню, Fancybox-попапы
├── assets/
│   ├── img/              # растровые картинки (hero-bg, cta-bg, лого, проекты, вебинары)
│   └── vendor/
│       ├── swiper/       # swiper-bundle (min.css + min.js), локально
│       └── fancybox/     # fancybox (css + umd.js), локально; подключается ТОЛЬКО на страницах, где используется
└── docs/
    ├── FIGMA_WORKFLOW.md # процесс: audit/implement/QA, измерения, допуски, bridge, дампы
    ├── FIGMA.md          # живой реестр: токены, компоненты, маппинг, статусы секций
    └── superpowers/
        ├── templates/    # шаблоны task (figma-section.md)
        └── plans/        # планы и отчёты сверки секций
```

Принципы (важнее конкретных файлов):
1. **Многостраничник, все страницы в корне.** Все `*.html` лежат в корне проекта (без подпапки `pages/`), поэтому пути из любого HTML: `assets/img/...`, `css/...`, `js/...` — без `../`. Ссылки между страницами — просто имена файлов: `href="solutions.html"`, `href="index.html"`.
2. **CSS — 5 файлов, каждый с одной зоной ответственности:** `tokens.css` (только переменные) → `utilities.css` (только универсальное; НЕ превращать в Tailwind-клон без необходимости) → `components.css` (повторяющиеся элементы) → `sections.css` (layout секций) → `media.css` (ТОЛЬКО @media-переопределения для адаптива). Подключаются в этом порядке. Порядок каскада: секции переопределяют компоненты, media.css переопределяет всё при той же специфичности. Новое адаптивное правило кладётся в `media.css`, а не в файл исходного стиля. Новый стиль кладётся по зоне, а не в первый попавшийся файл. Адаптация — прежде всего через токены: в `media.css` по брейкпоинтам меняем `:root`-переменные (`--fs-*`, `--section-py/-md/-px`, `--control-h`), компоненты и гриды переопределяем точечно. `html { font-size: 16px }` — постоянный, vw-зум не используем. Токены, не зависящие от ширины (`--gap-xs/sm/md`, `--radius-md/lg`), не адаптируются. Глобальный `transition: all` запрещён — только точечные переходы на интерактивных элементах.
3. **JS — `main.js` (одна инициализация).** Один `DOMContentLoaded`, внутри — init-функции: Swiper-слайдеры (7 шт., через фабрику `initSwiper`), `bindNav` для carousel-nav, аккордеоны, фильтры (clients/dropdown), попапы Fancybox, мобильное меню. Держать в одном файле; подпапки `js/components/` не нужны. Бургер/меню: CSS-брейкпоинт ≤1024 в media.css и resize-порог в `initMobileMenu` должны совпадать.
4. **Картинки** — в `assets/img/`, растровые. Пути: из HTML → `assets/img/...` (без `../`), из CSS → `../assets/img/...` (файл CSS лежит в `css/`). Никогда не наоборот.
5. **Иконки** — inline-SVG в каждой странице (vectorPaths из Figma). Отдельные файлы иконок НЕ создавать, пока иконка не переиспользуется между страницами. Стрелки — единый SVG-sprite: `#icon-arrow` (17×14, inbox, `fill="currentColor"`, стрелка для ссылок/блоков: карточки, задачи, проекты, вебинары) и `#icon-arrow-right` / `#icon-arrow-left` (15×14, стрелки для слайдеров: «Вперёд»/«Назад»). Подключение для ссылок/блоков: `<svg width="17" height="14" viewBox="0 0 17 14" aria-hidden="true"><use href="#icon-arrow"/></svg>`, для слайдеров: `<svg width="15" height="14" viewBox="0 0 15 14" aria-hidden="true"><use href="#icon-arrow-right"/></svg>`. НЕ использовать текст «→» и НЕ переворачивать CSS (`transform: scaleX(-1)`) — вместо этого вставлять правильную иконку.
6. **Шрифты** — Google Fonts `Inter` (400/500/600/700), подключать всегда через `<link>` в каждой странице (preconnect + css2 link). Локальные woff2 НЕ использовать. `--font-heading: 'Inter'`, `--font-body: 'Inter'`.

## Главный принцип (Architecture Rules)

1. **Figma — источник истины для визуального дизайна.** Существующая архитектура кода — источник истины для структуры реализации.
2. **Никогда не создавай новый CSS-класс, если элемент корректно выражается существующим компонентом или утилитой.**
3. **Перед созданием компонента:** 1) поискать в кодовой базе → 2) проверить, нет ли эквивалентного компонента → 3) проверить, не является ли элемент Figma вариантом существующего компонента.
4. **Не называй классы по визуальному назначению.** Figma naming ≠ code architecture. Figma «Blue Button» → `<a class="btn btn--primary">`, а не `blue-button`; «Large title» → `<h2 class="section-title">`, а не `large-title`; несколько вариантов → `<h2 class="section-title section-title--large">`. MCP читает Figma, но не копирует её названия в CSS автоматически.
5. **Component Registry.** При появлении новой секции агент СНАЧАЛА сверяет элемент с реестром ниже и переиспользует существующий компонент, а не создаёт страничный дубль. Пример: Figma показывает «Frame + Text» (кнопка) → искать `.btn`, а НЕ создавать `.projects__button`, если визуально и семантически это тот же компонент.
6. **Не переусложняй компонентами.** Не создавай reusable-компонент только потому, что элемент технически переиспользуем (для обычной кнопки НЕ нужны `ButtonText`/`ButtonIcon`/`ButtonWrapper`/`ButtonContainer`/`ButtonLabel`). Создавай компонент, когда: элемент встречается многократно, есть осмысленные варианты, есть поведение, либо это устойчивый паттерн дизайн-системы. Это важнее попытки сделать абсолютно всё reusable.
7. **Для каждой новой страницы — сначала Design Audit (FIGMA_AUDIT).** Не начинай сразу с Hero. Проанализировать страницу через Figma MCP, НЕ писать код, затем сравнить с существующей архитектурой и определить: 1) переиспользуемые компоненты, 2) компоненты под новый вариант, 3) новые компоненты, 4) новые design-токены, 5) страничные секции. Вернуть component mapping + план имплементации:

```
Figma                  Existing code
--------------------------------------------
Header                 .header
Primary button         .btn--primary
Section title          .section-title
Company card           .card--company
Slider                 .slider
New timeline           NEW: .timeline
New statistics         NEW: .stats
```

Это и есть правильная точка входа в новую страницу.
8. **После аудита — секции маленькими task-ами.** Task субагенту крошечный: секция, URL фрейма, node ID и РАЗРЕШЁННЫЙ набор компонентов из реестра (`Reuse: .container, .section-title, .card--company, .btn, .slider`). Субагент не создаёт дубликаты разрешённых компонентов; если существующий компонент не точно совпадает с вариантом Figma — сначала решить, уместен ли модификатор, и только при действительно ином паттерне создавать новый. В конце — процедура сверки из FIGMA_WORKFLOW.md. Шаблон: `docs/superpowers/templates/figma-section.md`.
9. **Разделяй Figma MCP задачи на типы.** Не смешивай в одном агенте анализ, архитектурное решение, код и рефакторинг: `FIGMA_AUDIT` (только читает Figma), `FIGMA_IMPLEMENT` (меняет код), `FIGMA_QA` (только проверяет). Подробности — в FIGMA_WORKFLOW.md.
10. **Разделяй page-specific и shared.** Shared-компоненты (кнопки, карточки, заголовки, слайдеры) — общие, переиспользуются между страницами. Page-specific (hero, industries, stats, tasks, companies, partners, projects, webinars, cta) — живут как секции. Если другая страница использует тот же блок (например companies) — переиспользуй ту же секцию/компонент. Если дизайн немного отличается — используй модификатор:

```
<section class="companies companies--compact">
```

а НЕ:

```
<section class="companies-page-2">
```

11. **Архитектурный review после каждой страницы.** Когда страница закончена — сделать review архитектуры, НЕ меняя визуальный результат. Искать: дублированный CSS, дублированные компоненты, почти-одинаковые селекторы, page-specific классы, которые должны быть shared, дублированные SVG, дублированные значения спейсинга/типографики, лишние обёртки, несогласованные имена, лишний JS. НЕ рефакторить сразу — вернуть план рефакторинга. После утверждения человеком — реализовать рефакторинг так, чтобы визуальный результат остался неизменным.
12. **FIGMA.md — живой реестр.** Параллельно с версткой вести `FIGMA.md`: маппинг Figma → Code (токены, компоненты, секции по страницам со статусами), чтобы следующая страница не изобретала архитектуру заново. Агент ОБЯЗАН проверять FIGMA.md перед созданием нового компонента. Workflow проекта — в FIGMA_WORKFLOW.md.

Главное: НЕ гнаться за отсутствием всех page-specific классов — `hero`, `tasks`, `projects` нормальные классы. Плохо не наличие секционных классов, а дублирование компонентов внутри них. Цель: section-specific layout + shared components + shared tokens + shared behavior, а НЕ один гигантский глобальный CSS и НЕ полностью изолированный CSS на каждый фрейм.

## Component vs Section Decision

Порядок решения перед созданием CSS-класса или компонента:

1. Это глобальный design token? → `tokens.css`
2. Это переиспользуемый UI-паттерн в нескольких местах/страницах? → `components.css`
3. Это существующий компонент с визуальным вариантом? → модификатор, а не новый компонент
4. Это layout/контент конкретной секции? → `sections.css`
5. Это разовый элемент внутри существующей секции? → BEM-класс секции только при необходимости

Никогда не создавай новый shared-компонент только потому, что Figma содержит frame. Frame Figma — дизайн-объект, а не автоматически код-компонент. Figma `Frame > Frame > Text + Vector` НЕ означает `.card-wrapper` / `.card-content` / `.card-icon` / `.card-text`.

## Figma Structure vs DOM

Структура Figma — для понимания визуальной композиции. Это НЕ требование дословно воспроизводить дерево узлов Figma. DOM должен оставаться семантическим, доступным, минимальным, поддерживаемым. Не добавляй обёртки только ради повторения иерархии фреймов Figma. Проверяй: количество визуальных элементов, порядок, содержимое, семантические связи, повторяющиеся компоненты, layout-отношения. НЕ требуй 1:1 соответствия каждого фрейма Figma каждому элементу DOM.

## Token Rules

Не создавай и не меняй design token только чтобы починить одну секцию. Перед добавлением токена: 1) проверить, нет ли значения уже; 2) проверить, встречается ли значение в нескольких фреймах Figma; 3) определить, действительно ли это значение дизайн-системы. Если значение секционное — оставить в CSS секции, а не засорять `tokens.css`. Никогда не добавляй произвольные токены вроде `--hero-padding-37`, `--projects-gap-13`, `--section-margin-42`.

Радиусы: 50px — конкретный радиус кнопки (см. `components.css`/`sections.css`), НЕ глобальный design token; 20px — радиус карточек. Пока в `tokens.css` радиусы лежат как `--radius-*` — это допустимо, но не добавляй новые радиусы под каждую секцию.

## Responsive: как устроен media.css

Файл двухслойный, это важно понимать до любых правок:

1. **Шапка — токен-лестница**: `:root`-тиры на 1600/1440/1280/1024/768/576 + структурные правила, которых нет в секционных блоках (container, бургер/мобильное меню, экосистема, хедер).
2. **Хвост — покомпонентные блоки** секций (hero, industries, stats, …) по тем же брейкпоинтам. Хвост идёт последним и **авторитетен при конфликте** с шапкой.

Правила:
- Прежде чем добавлять адаптивное правило в шапку — проверь, нет ли уже настроенного блока секции в хвосте (гриды `industries__grid`, `stats__grid` там уже перестраиваются по тирам; дубли в шапке = мертвый код).
- Бургер появляется ровно с ≤1024; `.header__contacts` скрыты с ≤1280 (при 16px root контакты не помещаются в диапазоне 1025–1280); на мобильных паддинги `.header__inner` привязаны к `--section-px`.
- `!important` в проекте ноль — не появляться.
- QA-паттерн: chrome-devtools эмуляция ширины → проверка `document.scrollWidth > clientWidth` (горизонтальный скролл) на 1440/1280/1024/768/375 + проба computed styles изменённых правил.

## Правила HTML и верстки

1. **1:1 по макету визуально.** Макет 1920px. Контентный контейнер: отступы по 40px, ширина контента 1790px (`--section-px`, `.container`). 1:1 относится к визуалу, НЕ к DOM-дереву Figma.
2. **Секции.** Каждая секция = отдельный `<section class="...">` в `index.html` (или в страничных `solutions.html`/`solution-detail.html`/`projects.html`/`clients.html`/`client-detail.html`) + блок CSS в `sections.css`. Классы БЭМ-подобные, без вложенных селекторов без надобности.
3. **Переменные.** Все цвета/размеры/отступы/радиусы — из `:root` в `css/tokens.css`. Значения только из токенов макета (но не плоди токены под каждую секцию).
4. **Картинки** — в `assets/img/`, пути: из HTML `assets/img/...`, из CSS `../assets/img/...`. Hero/CTA-фоны — через `<img>` или CSS-фон секции.
5. **Гриды карточек.** Отрасли: 4 × 460px, gap 10. Партнёры/проекты/вебинары: карточки 460/930px, gap 10, при переполнении — горизонтальная прокрутка (карусель) с overflow-x.
6. **Интерактив** в `js/main.js`: hover-список задач (плавный фон-картинка), swiper-слайдеры (клиенты, партнёры, проекты, вебинары; локально в `assets/vendor/swiper/`), кнопки каруселей (`carousel-nav`) управляют слайдерами.
7. **CSV/данные** подключаются кодом (fetch + рендер), не вставляются статично в HTML. Это отдельная архитектурная деталь: при визуальной сверке с Figma data flow НЕ менять.
8. **Шрифты** — Google Fonts `Inter` (400/500/600/700), подключать всегда через `<link>` в каждой странице. Локальные woff2 НЕ использовать.
9. После каждой секции — проверка в браузере (скриншот), сверка размеров с макетом по процедуре FIGMA_WORKFLOW.md (relative координаты, допуски ±1px).
10. Валидный HTML5, семантические теги, alt-тексты, aria для интерактива.
